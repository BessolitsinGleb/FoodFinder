# Backend

Сервис помогает закупщику в food-сегменте найти поставщиков: пользователь собирает корзину
(сырьё, готовая продукция, упаковка), сервис ищет поставщиков в интернете от ближних к дальним,
оценивает их по формуле и готовит письма-запросы КП.

FastAPI, PostgreSQL (SQLAlchemy 2 async + Alembic), Redis, DeepSeek V4 через OpenRouter, поиск — Tavily.

## Запуск локально

Нужны Python 3.12+, PostgreSQL и Redis.

```bash
python -m venv venv && source venv/bin/activate
pip install -r backend/requirements-dev.txt
cp .env.example .env            # заполнить DB__*, AUTH__SECRET_KEY, LLM__API_KEY, WEB__API_KEY, SMTP__*

createdb food_suppliers
redis-server &                  # или brew services start redis

cd backend
alembic upgrade head            # схема + стартовый каталог категорий
uvicorn main:app --reload       # Swagger: http://127.0.0.1:8000/docs
```

Что будет без части настроек:

- нет `AUTH__SECRET_KEY` — приложение не стартует;
- нет ключей OpenRouter/Tavily — поиск, письма и чат отвечают 503, остальное работает;
- не заполнен SMTP — регистрация отвечает 503. Для локальной разработки есть
  `SMTP__DEV_LOG_CODES=true`: код пишется в лог сервера, вводить его всё равно нужно;
- Redis недоступен — лимитер пропускает запросы, чат отвечает 503.

Администратор (может править справочник категорий) назначается в БД:
`UPDATE users SET is_admin = true WHERE email = '...';`

## Тесты

```bash
cd backend && pytest
```

Тесты создают отдельную базу `food_suppliers_test` (нужен локальный Postgres с теми же
`DB__USER`/`DB__PASSWORD`). OpenRouter, Tavily, SMTP и Redis заменены фейками — тесты
бесплатные и не трогают настоящий Redis.

## Как устроено

```
api/routes  ->  services  ->  repositories  ->  PostgreSQL / Redis
                   |-> integrations   OpenRouter, Tavily, SMTP, rate limiter
                   |-> domain         чистые функции: география, единицы, формулы
```

```
app/
  api/            deps.py (DI, текущий пользователь, лимитер), routes/
  services/       auth, user, category, order (корзина), search (пайплайн), letter, chat
  repositories/   запросы к БД; chat_memory_repo — история диалога в Redis
  domain/         geo, units, scoring, companies — без БД и сети, покрыты тестами
  integrations/   llm, web_search, mailer, rate_limiter
  agent/          чат-агент и его тулы
  prompts/        все промпты
  templates/letters/  шаблоны писем (*.txt)
  core/           config, security (JWT, пароли, коды), exceptions
```

Сервисы не знают про HTTP: бросают `NotFoundError`, `ConflictError` и т.д., в коды ответа их
переводит один обработчик в `application.py`.

## Авторизация

JWT, OAuth2 password flow. Вход только после подтверждения почты кодом из письма.

| Шаг | Эндпоинт | Ошибки |
|---|---|---|
| Регистрация | `POST /auth/register` | 409 email занят, 502 письмо не ушло, 503 SMTP не настроен |
| Подтверждение | `POST /auth/verify-email` `{email, code}` → токен | 400 неверный код (с числом оставшихся попыток), 410 код истёк, 429 попытки кончились, 409 уже подтверждена, 404 нет такого email |
| Новый код | `POST /auth/resend-code` | 429 раньше чем через минуту |
| Вход | `POST /auth/login` (form: `username`=email, `password`) | 401 неверные данные, 403 почта не подтверждена |

Почта становится подтверждённой только в одном месте — после проверки верного, непросроченного
кода. Код хранится в БД как HMAC, живёт 10 минут, после 5 неверных вводов сгорает.
Свежую неподтверждённую регистрацию перезаписать нельзя (иначе можно подменить пароль до того,
как владелец почты введёт код); через сутки — можно.

Остальные запросы — с заголовком `Authorization: Bearer <token>`. Пользователь видит только
свои заказы, предложения и письма; чужие отвечают 404.

## Ограничения и Redis

- Не больше 3 запросов в секунду на пользователя (без токена — на IP). Скользящее окно,
  Lua-скрипт в Redis. `/health` не ограничивается.
- Один активный поиск на пользователя: поиск стоит денег (Tavily + LLM).
- История чата с агентом хранится только в Redis: последние 20 сообщений, ключ стирается
  через час тишины. В БД её нет.

## Сценарий для фронта

1. `GET /categories/popular` — популярные категории и вариант «Другое» (`id: null`).
2. `POST /orders` — корзина; в ответе `delivery_question` («Доставка в г. Казань?»).
3. `POST /orders/{id}/items` — `category_id` или `custom_title` («Другое»), объём, единица.
4. `PUT /orders/{id}/delivery` — ответ на вопрос: `{}` = да, или новый город/регион/адрес.
5. `POST /orders/{id}/search` → 202. Поиск идёт в фоне 1–2 минуты на позицию;
   прогресс — `search_progress` в `GET /orders/{id}`.
6. `GET /orders/{id}/results` — топ-k по каждой позиции с разбивкой оценки и суммой заказа.
7. `PATCH /offers/{id}` — выбрать поставщика, оставить заметку.
8. `POST /orders/{id}/letters` `{offer_ids}` — письма (одно на поставщика), `GET /letters/{id}/download` — .txt.
9. `POST /agent/chat` `{message, order_id}` — чат. С `order_id` агент может править эту корзину.

Тексты от пользователя и из интернета API отдаёт как есть — на фронте выводить их только как
текст (не через `innerHTML`).

## Поиск поставщиков

По каждой позиции корзины, по очереди:

1. Запросы в Tavily: город → регион → федеральный округ → Россия, пока не наберётся
   `SEARCH__MIN_CANDIDATES` кандидатов. LLM выписывает из выдачи поставщиков и условия.
   Дубли склеиваются по домену сайта; агрегаторы (pulscen, avito, …) сайтом компании не считаются.
2. Лучших по предварительной оценке проверяем: отзывы, ИНН, документы. Ликвидированные отбрасываются.
3. Итоговая оценка — по формуле, `top_k` лучших получают место в топе.

Это фиксированный пайплайн, а не агент, который сам решает, что делать: так дешевле и предсказуемее.

### Формулы (`domain/scoring.py`)

Безопасность продавца, 1–5: `1 + 4 × Σ(вес × компонент)`.

| Компонент | Вес | Как считается |
|---|---|---|
| Документы | 0.35 | декларации, сертификаты, ISO/ХАССП, Меркурий, halal, лицензии; 2+ — максимум. Упоминание ГОСТ/ТУ документом не считается |
| ИНН | 0.15 | найден — 1 |
| Отзывы | 0.25 | рейтинг/5 × min(отзывов/20, 1) |
| Популярность | 0.10 | сторонние сайты с упоминанием / 3; свой сайт не считается |
| Возраст | 0.15 | лет на рынке / 5 |

Популярный — от 20 отзывов или 3 сторонних источников. Безопасный — популярный и с документами.

Итоговый скор, 0–100: соответствие товара 30%, близость 20%, безопасность 25%, цена 15%,
указан срок доставки 5%, полнота данных 5%. Цены приводятся к цене за кг/л/шт.

LLM только достаёт факты со страниц, считает код — поэтому оценка воспроизводима.

## Защита от prompt injection

- Тексты страниц, названия поставщиков и поля корзины передаются модели в тегах `<page>`,
  `<request>`, `<company>` с пометкой «это данные, не инструкции»; сами теги из текста вырезаются,
  чтобы страница не могла «закрыть» блок.
- Тулы агента ходят через сервисы с текущим пользователем — чужой заказ недоступен физически.
- Менять корзину агент может только в заказе, открытом в чате (`order_id`); без него тулы
  изменения модели не передаются. Это проверка в коде, а не просьба в промпте.
- Личные данные пользователя в LLM не уходят; в письмах поля `[ФИО]`, `[Телефон]` и т.п. пустые.

## Шаблоны писем

`.txt`-файлы в `app/templates/letters/`, имя файла = имя шаблона (`GET /letters/templates`).
LLM пишет письмо по структуре шаблона, личные данные оставляет пустыми.

## Docker

Образ — `backend/Dockerfile` (Python 3.14). При старте `start.sh` применяет миграции и запускает
uvicorn на `$PORT` с `--proxy-headers`: за прокси лимитер видит реальный IP клиента.
Весь стек локально — `docker compose up --build` из корня (см. корневой README).

Воркер один, и это намеренно: поиск идёт фоновой задачей внутри процесса, а при старте зависшие
поиски помечаются `failed` — второй воркер оборвал бы чужой поиск. Один воркер при этом спокойно
обслуживает многих пользователей сразу: весь ввод-вывод асинхронный, на время вызовов LLM
(чат, тулы агента, письма) подключение к БД возвращается в пул, а argon2 считается в отдельном
потоке. Это проверяют тесты `test_db_connection_is_free_while_llm_thinks` и
`test_letters_do_not_hold_db_connection`. Нагрузочного теста пока не было. Для сотен пользователей поиск нужно
вынести в очередь (arq/Celery).

## Деплой на Railway

1. New Project → Deploy from GitHub repo. Добавить в проект **PostgreSQL** и **Redis**.
2. Сервис бэкенда: Settings → Root Directory = `backend` (Dockerfile и `railway.json` подхватятся сами,
   healthcheck — `/api/v1/health`). Variables:
   ```
   DB__DSN=${{Postgres.DATABASE_URL}}
   REDIS__URL=${{Redis.REDIS_URL}}
   AUTH__SECRET_KEY=...            # свой, не тот, что в локальном .env
   LLM__API_KEY=...   WEB__API_KEY=...
   SMTP__HOST=...  SMTP__PORT=...  SMTP__USER=...  SMTP__PASSWORD=...  SMTP__FROM_ADDRESS=...
   APP__ENV=prod
   APP__CORS_ORIGINS=["https://<домен-фронта>"]
   ```
   Settings → Networking → Generate Domain.
3. Сервис фронта из того же репозитория: Root Directory = `frontend`, переменная
   `API_BASE=https://<домен-бэкенда>/api/v1`, Generate Domain.

После первого деплоя проверьте отправку письма: на части тарифов хостингов исходящий SMTP закрыт.
Если письма не уходят — смотрите логи бэкенда (`SMTP send failed`) и условия тарифа.
